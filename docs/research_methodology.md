## 2. Протокол разделения выборки (Split & Leakage Policy)

Для исключения переобучения и методологических утечек данных (Data Leakage) фиксируется следующая иерархия разделения:

```text
Официальный SROIE Train (626 документов)
          │
          ├──► Development Split (N = 500, seed 42): разработка алгоритмов, отладка кода
          └──► Validation Split  (N = 126, seed 42): калибровка параметров деградаций и препроцессинга

Официальный SROIE Test (347 документов) ──► СТРОГО ИЗОЛИРОВАННЫЙ ТЕСТ (NO TUNING)
          │
          ├──► Main Experiment Subset (N = 100, seed 42): быстрые матричные прогоны
          └──► Full Test Verification  (N = 347): финальное подтверждение результатов в дипломе
```

### Правила предотвращения Data Leakage:
1. **Split-before-synthesis:** Разбиение на `train_internal`, `validation` и `test` выполняется строго на уровне уникальных идентификаторов исходных документов (`document_id`) до генерации деградаций. Никакие синтетические варианты одного физического чека не могут пересекаться между сплитами.
2. **Изоляция тестовой выборки:** Любая калибровка параметров деградаций, настройка порогов препроцессинга и подбор архитектур моделей производятся **исключительно на `validation` сплите ($N=126$)**. Тестовый сплит открывается только для финального замера метрик.
3. **Информационный барьер модуля KIE:** Во время инференса модуль KIE получает на вход **исключительно** объект `OCRResult` (и опционально изображение). Доступ к `OCRGroundTruth`, `KIEGroundTruth` или именам целевых файлов во время предсказания полностью изолирован.

## 3. Семантика шкалы Severity и процедура калибровки

### 3.1. Определение шкалы
Зафиксирована единая дискретная шкала интенсивности деградаций:
$$\text{severity} \in \{0, 1, 2, 3, 4\}$$

* **`severity = 0` (Control Reference):**  
  Оригинальное изображение из датасета **без наложения синтетических деградаций**. Это контрольная точка с естественными артефактами бумаги (замятия, выцветание термобумаги, шум камеры).
* **`severity = 1` (Mild):**  
  Слабая степень деградации, незначительно снижающая визуальный контраст или резкость.
* **`severity = 2` (Moderate):**  
  Умеренная степень деградации, заметная при беглом взгляде, но сохраняющая общую читаемость человеком.
* **`severity = 3` (Strong):**  
  Сильная степень деградации, приводящая к разрушению мелких деталей шрифта.
* **`severity = 4` (Severe):**  
  Критическая степень деградации, предельно затрудняющая зрительное восприятие текста.

### 3.2. Процедура будущей калибровки параметров
Конкретные физические параметры (значения $\sigma$ для размытия, уровень дисперсии шума, качество JPEG, угол наклона) **не хардкодятся на этапе методологии**, а подлежат эмпирической калибровке в рамках последующей задачи реализации Degradation Engine по следующему регламенту:
1. Формирование сетки кандидатных параметров для каждого типа деградации.
2. Прогон на выборке `validation` ($N=126$).
3. Визуальный контроль и проверка монотонности изменения физических метрик искажения (PSNR / SSIM).
4. Утверждение фиксированного словаря параметров в YAML-конфигурациях.

## 4. Двухуровневый протокол оценки OCR

Деградация входного изображения влияет как на локализацию строк (детекцию), так и на распознавание глифов (символов). В исследовании фиксируются два взаимодополняющих протокола:

### 4.1. Primary Protocol: End-to-End OCR (Основной эксперимент)
* **Схема:** `Изображение → Детекция текста → Распознавание символов → Reading Order → OCRResult`.
* **Reading Order (Порядок чтения):** Сортировка распознанных боксов сверху-вниз по вертикальной координате $y_{min}$ (с допуском на строку $\Delta y \approx 0.5 \times \text{высота строки}$), затем слева-направо по горизонтальной координате $x_{min}$. Строки объединяются через символ переноса `\n`.
* **Обработка краевых случаев:**
  * *Пропущенные регионы (False Negatives):* учитываются как символьные удаления ($D_c$) в расстоянии Левенштейна.
  * *Ложные регионы (False Positives / шум):* учитываются как символьные вставки ($I_c$).
  * *Пустой вывод OCR:* фиксируется $\text{CER} = 1.0$, $\text{WER} = 1.0$, $\text{Char-NED} = 0.0$.
* **Роль:** Основная метрическая оценка практической устойчивости Document AI системы.

### 4.2. Diagnostic Protocol: GT-Region Recognition (Диагностический эксперимент)
* **Схема:** `Изображение + Эталонные GT Bounding Boxes → Кроп регионов → Распознавание символов → OCRResult`.
* **Роль:** Вспомогательный диагностический инструмент. Позволяет ответить на вопрос, вызвано ли падение качества KIE сбоем локализации боксов или ошибками транскрипции символов.
* **Ограничение:** Диагностический эксперимент **не заменяет** и не отменяет основной End-to-End протокол.

## 5. Политика Ground Truth: Raw GT vs Normalized Evaluation

> ⚠️ **Фундаментальный принцип:** Dataset Adapter обязан возвращать **абсолютно неизмененный эталон (Immutable Raw GT)**. Любая модификация исходных строк на этапе загрузки данных запрещена.

В Evaluator вводятся два независимых режима оценки:
1. **Raw Evaluation Mode:** Сравнение предсказания модели напрямую с Raw GT (`pred == gt`).
2. **Normalized Evaluation Mode:** Сравнение после симметричного применения функции нормализации:
   $$\text{Matched} \iff \text{Normalize}(V_{pred}) == \text{Normalize}(V_{gt})$$

### Спецификация правил симметричной нормализации KIE:

| Поле | Входное значение (Input) | Применяемая трансформация (Transformation) | Возможные сбои и граничные случаи (Failure Modes) |
| :--- | :--- | :--- | :--- |
| **`date`** | Строка даты в произвольном формате (`27/12/2017`, `27-Dec-17`, `2017.12.27`) | Регулярный парсинг дня, месяца, года $\to$ приведение к каноническому формату ISO-8601: `YYYY-MM-DD` | Двусмысленные форматы (`01/02/03`), опечатки OCR в названии месяца (`J4N` вместо `JAN`). При неудаче парсинга: возврат очищенной lowercase-строки без пунктуации. |
| **`total`** | Денежная сумма (`$ 4.50`, `TOTAL: 1,234.50`, `RM4.50`) | Удаление префиксов валют (`$`, `RM`, `USD`, `TOTAL`), удаление разделителей тысяч (пробелы, запятые), замена десятичной запятой на точку, приведение к `float` с округлением до 2 знаков (`4.50`) | Несколько точек/запятых, слияние знака валюты с цифрой при ошибке OCR (`B4.50` вместо `$4.50`). При неудаче: возврат очищенной цифровой последовательности. |
| **`company`** | Название организации/магазина | Приведение к lowercase, удаление знаков пунктуации, схлопывание повторных пробелов в одиночный | Различия в юридических формах (`SDN BHD`, `LTD`, `BHD`). |
| **`address`** | Почтовый адрес организации | Приведение к lowercase, замена запятых, точек и переносов строк на пробелы, схлопывание пробелов | Ошибки OCR в почтовых индексах (распознавание цифры `5` как `S`, `0` как `O`). |

## 6. Система метрик

### 6.1. Метрики OCR
* **Primary:**
  * **CER (Character Error Rate):** $\text{CER} = \frac{S_c + D_c + I_c}{N_c}$.
  * **WER (Word Error Rate):** $\text{WER} = \frac{S_w + D_w + I_w}{N_w}$.
* **Secondary:**
  * **Character-NED (Normalized Edit Distance):** $1 - \frac{\text{Levenshtein}(T_{pred}, T_{gt})}{\max(|T_{pred}|, |T_{gt}|)}$.
* **OCR Text Normalization:** При расчете CER/WER выполняется Unicode NFC нормализация, удаление невидимых служебных символов и схлопывание горизонтальных пробелов (без изменения семантики текста).

### 6.2. Метрики KIE
* **Primary Analytical:**
  * **Field-level F1, Precision, Recall** по каждому из 4 полей (`company`, `date`, `address`, `total`).
  * **Macro F1:** Несмещенное среднее арифметическое F1 по всем полям документа:
    $$\text{Macro } F_1 = \frac{1}{|\mathcal{F}|} \sum_{f \in \mathcal{F}} F_1^{(f)}$$
  * **Document-level Exact Match (Doc-EM):** Доля документов, в которых все 4 целевых поля извлечены безошибочно.

## 7. Экспериментальная иерархия Preprocessing

Вводятся три обязательных экспериментальных слоя:
* **B0 (Clean Reference):** `Original (Severity 0) → OCR → KIE`
* **B1 (Degraded Unmitigated):** `Original → Degradation (Severity 1..4) → OCR → KIE`
* **B2 (Degraded Mitigated):** `Original → Degradation (Severity 1..4) → Preprocessing → OCR → KIE`

### Кандидаты методов предварительной обработки (без хардкода параметров):
1. **Grayscale conversion** (устранение цветового шума).
2. **Denoising** (фильтрация аддитивного высокочастотного шума: Median, Bilateral, FastNlMeans).
3. **Contrast Enhancement** (CLAHE — локальная эквализация гистограммы).
4. **Binarization** (адаптивная пороговая бинаризация: Otsu, Sauvola).
5. **Deskew** (детекция угла наклона через преобразование Хафа / MinAreaRect).

Конкретные гиперпараметры фильтров будут подобраны на выборке `validation` ($N=126$).

## 8. Статистический протокол и отчетность (Statistical Reporting)

Для устранения статистической нестабильности результаты оцениваются по следующим правилам:
1. **Агрегированные статистики:** Для каждой точки кривой робастности рассчитываются:
   * Среднее значение (Mean);
   * Медиана (Median);
   * Стандартное отклонение (Standard Deviation);
   * 95% доверительный интервал (95% Bootstrap Confidence Interval на 1,000 итераций сэмплирования).
2. **Роль подвыборок:**
   * $N=100$ используется как **development-scale evaluation subset** для быстрой отладки матриц и гипотез.
   * Окончательные научные выводы и таблицы диплома верифицируются на **полном тестовом сплите ($N=347$)**.

## 9. Исследовательские вопросы (Research Questions)

* **RQ1:** Как различные типы и уровни severity деградаций изображения влияют на метрики качества сквозного распознавания текста (End-to-End CER и WER)?
* **RQ2:** Как деградация входного изображения влияет на точность извлечения ключевых семантических полей (KIE Macro F1 и Document-level Exact Match)?
* **RQ3:** Каков характер взаимосвязи между ухудшением качества распознавания текста (рост CER) и падением точности извлечения сущностей (снижение F1) — носит ли эта связь линейный или пороговый характер?
* **RQ4:** В каких условиях и при каких типах деградаций предварительная обработка изображений повышает устойчивость связки OCR/KIE, а в каких — приводит к ухудшению результатов?

## 10. Проверяемые гипотезы (Testable Hypotheses)

* **H1:** Увеличение severity деградации в среднем приводит к монотонному ухудшению метрик OCR (рост CER и WER), однако скорость деградации и форма кривой статистически значимо различаются между различными типами искажений.
* **H2:** Различные типы деградаций формируют качественно различные профили устойчивости: искажения, нарушающие глобальную геометрию (перспективный наклон, поворот), оказывают более сильное разрушительное воздействие на сквозной пайплайн, чем аддитивные шумы при сопоставимой визуальной заметности.
* **H3:** Ухудшение качества OCR статистически связано со снижением качества KIE, однако эта зависимость является нелинейной: числовые поля (`total`, `date`) демонстрируют более резкий спад точности при возникновении локальных ошибок распознавания, чем протяженные текстовые поля (`company`, `address`).
* **H4:** Эффективность предварительной обработки зависит от типа деградации и её интенсивности: при определенных условиях препроцессинг статистически значимо повышает устойчивость системы, однако при несовпадении фильтра с физикой шума или при экстремальных уровнях искажения препроцессинг может ухудшать итоговые метрики.

## 11. Угрозы валидности (Threats to Validity)

* **Синтетический характер деградаций (Construct Validity):**  
  * *Угроза:* Синтетические фильтры могут упрощать сложные нелинейные оптические артефакты реального мира.  
  * *Контроль (Mitigation):* Параметры деградаций калибруются по физическим характеристикам реальных мобильных фотографий чеков; в расширенном исследовании применяются комбинированные деградации.
* **Смещение при настройке параметров (Internal Validity):**  
  * *Угроза:* Завышение робастности из-за переобучения фильтров под тестовые изображения.  
  * *Контроль (Mitigation):* Строгая изоляция: вся калибровка препроцессинга проводится на выборке `validation` ($N=126$); тестовый сплит ($N=347$) обрабатывается вслепую.
* **Ограниченность домена чеков (External Validity):**  
  * *Угроза:* Выводы на чеках SROIE могут иметь ограниченную переносимость на другие классы документов (многостраничные договоры, анкеты).  
  * *Контроль (Mitigation):* Архитектура спроектирована через `BaseDatasetAdapter` для валидации на FUNSD и DocILE в перспективе; границы применимости четко оговариваются в дипломной работе.
* **Статистическая погрешность (Conclusion Validity):**  
  * *Угроза:* Случайные флуктуации метрик на небольших подвыборках.  
  * *Контроль (Mitigation):* Промежуточные результаты снимаются на $N=100$, а финальные — на полном сплите $N=347$; рассчитываются 95% bootstrap доверительные интервалы для всех графиков.
