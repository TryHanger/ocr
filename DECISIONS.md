# Architectural Decision Records (ADR)

Журнал фиксации архитектурных решений проекта «Качество скана и устойчивость OCR/KIE к деградациям».

---

## ADR-001: Модульная структура репозитория
* **Status:** Accepted (2026-09-26)
* **Decision:** Организовать проект в виде независимых пакетов внутри `src/`: `degradation`, `preprocessing`, `ocr`, `kie`, `evaluation`, `visualization`, с четким разделением конфигураций (`configs/`), скриптов (`scripts/`), тестов (`tests/`) и Kaggle-окружения (`kaggle/`).
* **Context:** Исследовательский проект требует гибкости для изолированного тестирования каждого этапа пайплайна без взаимного спагетти-кода.
* **Alternatives:** Монолитный скрипт или организация вокруг Jupyter-ноутбуков.
* **Rationale:** Ноутбуки плохо поддаются версионированию, автоматизированному тестированию и запуску матриц экспериментов. Четкая структура пакетов обеспечивает модульность и поддерживаемость.
* **Consequences:** Необходимость определять строгие контракты данных (DTO) между слоями.

## ADR-002: Конфигурационное управление экспериментами (Config-Driven Architecture)
* **Status:** Accepted (2026-09-26)
* **Decision:** Все параметры экспериментов (тип деградации, severity, шаги препроцессинга, настройки OCR, правила метрик, random seed) задаются через иерархические YAML-файлы в директории `configs/`.
* **Context:** Проведение матричных экспериментов и обеспечение их научной воспроизводимости требует исключить хардкод параметров в исполняемом коде.
* **Alternatives:** Передача всех параметров через аргументы командной строки (argparse/click) или глобальные переменные в Python файлах.
* **Rationale:** Файлы YAML легко версионируются, валидируются и могут сохраняться в директорию запуска вместе с полученными метриками для 100% аудируемости результатов.
* **Consequences:** Требуется наличие библиотеки PyYAML и схемы валидации конфигурационных файлов.

## ADR-003: Разделение слоев Degradation, Preprocessing, OCR, KIE и Evaluation
* **Status:** Accepted (2026-09-26)
* **Decision:** Каждый из пяти этапов экспериментального пайплайна проектируется как полностью независимый компонент с контрактом обмена через простые типы (`numpy.ndarray`, DTO/dataclasses):
  - Degradation: `(Image, severity, seed) -> DegradedImage`
  - Preprocessing: `(DegradedImage, params) -> EnhancedImage`
  - OCR: `(Image) -> OCRResult (text, bboxes, confidences)`
  - KIE: `(OCRResult, Image?) -> KIEResult (fields, confidences)`
  - Evaluation: `(Prediction, GroundTruth) -> Metrics`
* **Context:** Необходимо иметь возможность заменять один компонент (например, менять метод OCR или отключать препроцессинг) без модификации кода остальных модулей.
* **Alternatives:** Сквозной пайплайн, где препроцессинг встроен в модуль OCR, а KIE жестко завязан на конкретный формат вывода конкретной OCR-библиотеки.
* **Rationale:** Сквозная привязка делает невозможным проведение абляционных исследований (ablation study) и изоляцию источника ошибок.
* **Consequences:** Потребуется написать адаптеры для приведения вывода различных OCR/KIE библиотек к единому формату DTO.

## ADR-004: Протокол воспроизводимости (Reproducibility Protocol)
* **Status:** Accepted (2026-09-26)
* **Decision:** Каждый генератор деградаций и случайных преобразований должен явно принимать и фиксировать `seed`. Для каждого эксперимента фиксируется глобальный random seed, записываемый в итоговый артефакт.
* **Context:** В научных исследованиях недетерминированные искажения изображений делают невозможным прямое попарное сравнение эффективности алгоритмов предобработки.
* **Alternatives:** Случайная генерация на лету без фиксации состояния генератора псевдослучайных чисел.
* **Rationale:** Одинаковый исходный документ + одинаковый seed + одинаковый severity обязаны давать попиксельно идентичную деградацию.
* **Consequences:** Необходимость написания unit-тестов, проверяющих детерминизм деградаций по seed.

## ADR-005: Выделение Kaggle как отдельной execution target
* **Status:** Accepted (2026-09-26)
* **Decision:** Выделить директорию `kaggle/` для размещения скриптов автоматизации сборки и запуска ядра через официальный Kaggle API (`kaggle kernels push`).
* **Context:** Выполнение полного матричного эксперимента требует GPU-ресурсов, которые могут быть предоставлены облачной платформой Kaggle.
* **Alternatives:** Разработка непосредственно в веб-ноутбуках Kaggle с последующим ручным переносом кода в локальный репозиторий.
* **Rationale:** Локальная разработка в IDE с версионированием в Git и отправка готовых скриптов в Kaggle через CLI предотвращает рассинхронизацию кодовой базы и потерю истории коммитов.
* **Consequences:** Требуется разработать скрипт упаковки локального пакета `src/` для автономного импорта внутри окружения Kaggle.

## ADR-006: Дискретная шкала severity деградаций (целые числа 0–4)
* **Status:** Accepted (2026-09-26)
* **Decision:** Зафиксировать уровни интенсивности деградаций в `DegradationSpec` в виде строго целочисленной шкалы от 0 до 4:
  - `0`: исходное изображение без изменений (Identity / Clean baseline);
  - `1`: слабая деградация (mild);
  - `2`: умеренная деградация (moderate);
  - `3`: сильная деградация (strong);
  - `4`: критическая/разрушительная деградация (severe).
* **Context:** Для построения робастных кривых (Robustness curves: качество распознавания vs степень искажения) требуется дискретная ось X с сопоставимыми градациями между различными типами физических искажений (размытие, шум, сжатие, тени).
* **Alternatives:** Непрерывный float диапазон [0.0, 1.0] или задание физических параметров напрямую в эксперименте.
* **Rationale:** Дискретные уровни 0–4 позволяют легко агрегировать результаты по всей тестовой выборке и сравнивать разные алгоритмы в одинаковых реперных точках. Физические параметры (например, $\sigma$ размытия или Quality JPEG) однозначно маппируются на уровень severity внутри конфигурации генератора.
* **Consequences:** Каждый генератор деградаций обязан реализовать однозначное отображение дискретного уровня 0–4 на свои физические параметры.

## ADR-007: Использование стандартных dataclasses для DTO без внешних валидаторов
* **Status:** Accepted (2026-09-26)
* **Decision:** Реализовать все DTO в `src/core/schemas.py` на базе стандартных `dataclasses` со строгой валидацией в методе `__post_init__` и явными методами `to_dict()` и `from_dict()`.
* **Context:** Требовалось обеспечить строгую типизацию, проверку инвариантов и сериализацию без раздувания зависимостей проекта.
* **Alternatives:** Использование библиотеки Pydantic (v1/v2) или Attrs.
* **Rationale:** Введение Pydantic на этапе core-контрактов создает лишнюю тяжелую зависимость с потенциальными проблемами совместимости между версиями Python и платформами (особенно при переносе в Kaggle / минимальные контейнеры). Стандартный модуль `dataclasses` обеспечивает нулевой оверхед, отсутствие внешних зависимостей и прозрачное управление логикой валидации.
* **Consequences:** Необходимость явного написания логики валидации и десериализации вложенных структур в методах `from_dict()`.

## ADR-008: Выбор базового датасета SROIE и архитектура Dataset Adapter
* **Status:** Accepted (2026-09-26, уточнён в TASK-003-R1)
* **Decision:** 
  1. Выбрать **SROIE (ICDAR 2019 Robust Reading Challenge on Scanned Receipts)** в качестве Primary Benchmark для исследования устойчивости OCR/KIE к деградациям. В качестве Secondary Cross-Domain Validation зафиксировать **FUNSD** (без обязательной реализации в MVP), а **DocILE** — как Future Enterprise Extension.
  2. Зафиксировать архитектуру загрузки через абстрактный интерфейс `BaseDatasetAdapter` с конкретной реализацией `SROIEAdapter`.
  3. Для дипломных экспериментов зафиксировать подвыборки: Smoke test ($N=3..5$), Development ($N=25$), Main research experiment ($N=100$ из тестового сплита) с возможностью финального прогона на полном сплите ($N=361$).
  4. Зафиксировать, что `severity=0` означает оригинальное изображение из датасета (с его естественными артефактами бумаги и печати), а не идеальный синтетический документ.
  5. Запретить подбор гиперпараметров деградаций и препроцессинга на основном тестовом сплите (защита от Data Leakage).
* **Context:** Для исследования влияния физических деградаций сканов на связку OCR $\to$ KIE необходим датасет реальных документов с подтвержденным и независимым Ground Truth одновременно для распознавания текста (построчная транскрипция с координатами) и семантических полей (`company`, `date`, `address`, `total`), доступный для пакетного исполнения на Kaggle.
* **Alternatives:** 
  * FUNSD (слишком малый сплит $N=50$, исходно зашумлен архивными артефактами, KIE в виде графа вопрос-ответ).
  * CORD (индонезийский язык, 30 категорий меню усложняют интерпретацию).
  * DocILE (закрытый доступ по токену, многостраничные PDF, десятки гигабайт, перегрузят ресурсы).
* **Rationale:** SROIE является признанным академическим бенчмарком с RGB сканами/фотографиями, четкой 4-полевой KIE схемой, английским языком и встроенной доступностью на платформе Kaggle (`urbikn/sroie-datasetv2`). Архитектура `BaseDatasetAdapter` позволяет в будущем безболезненно подключить любой другой датасет.
* **Consequences:** Специфика документов ограничена кассовыми чеками и квитанциями. Для работы с SROIE требуется адаптер, преобразующий Task 1/2 `.txt` файлы и Task 3 `.json` в наши контракты `DocumentMetadata`, `OCRGroundTruth` и `KIEGroundTruth`.

## ADR-009: Двухуровневый протокол оценки OCR (End-to-End как Primary, GT-Region как Diagnostic)
* **Status:** Accepted (2026-09-26)
* **Decision:** Зафиксировать два взаимодополняющих протокола оценки OCR:
  1. **Primary Protocol (End-to-End OCR):** изображение подается целиком на вход OCR-модели, оценивается качество связки детекция + распознавание + reading order $\to$ KIE.
  2. **Diagnostic Protocol (GT-Region Recognition):** текст распознается по кропам эталонных bounding boxes из Ground Truth, что позволяет строго изолировать ошибки распознавания символов от ошибок детекции границ текста при анализе аномалий.
* **Context:** Деградации изображения одновременно влияют и на локализацию текстовых блоков (Detection), и на транскрипцию символов (Recognition). Необходимо исследовать реальный промышленный сквозной эффект, но иметь механизм точной диагностики первопричин сбоев.
* **Alternatives:** Использовать только Recognition по GT боксам (оторвано от реальности) либо только End-to-End (не позволяет понять, почему упало качество — из-за детектора или распознавателя).
* **Rationale:** End-to-End является основным сценарием Document AI, а GT-Region протокол используется для глубокого исследовательского анализа в дипломной работе.
* **Consequences:** Движок OCR должен поддерживать как режим полного распознавания изображения, так и распознавание по заданным полигонам/боксам.

## ADR-010: Политика неизменяемого Raw Ground Truth и изолированной семантической нормализации KIE
* **Status:** Accepted (2026-09-26)
* **Decision:**
  1. Датасет-адаптер обязан отдавать Ground Truth в строго неизменном, сыром виде (**Immutable Raw GT**). Запрещено модифицировать эталонный текст или форматы дат/сумм на уровне загрузки данных.
  2. Оценка OCR (CER, WER) производится по прямому строковому сопоставлению с Raw OCR GT.
  3. Для оценки KIE вводится централизованный модуль симметричной нормализации `Normalize()`, применяемый одинаково к предсказанию модели и эталону в момент вычисления метрик:
     $$\text{Matched} \iff \text{Normalize}(V_{pred}) == \text{Normalize}(V_{gt})$$
* **Context:** Без нормализации метрика KIE Exact Match катастрофически занижается из-за банальных различий форматирования (`01/02/2020` vs `2020-02-01`), однако мутация исходного GT на уровне адаптера лишает исследование объективности и маскирует реальный текст.
* **Alternatives:** Сравнение строк "как есть" (занижает F1) либо изменение файлов разметки самого датасета (нарушает воспроизводимость и чистоту бенчмарка).
* **Rationale:** Изолированная симметричная нормализация в момент evaluation гарантирует чистоту данных и объективность замеров.
* **Consequences:** Необходимость строгой спецификации и тестирования правил нормализации для каждого типа целевых полей.

## ADR-011: Семантика шкалы Severity и спецификация экспериментальной единицы
* **Status:** Accepted (2026-09-26)
* **Decision:**
  1. `severity = 0` строго определяется как контрольный оригинал документа из датасета (Control Reference) без синтетических деградаций.
  2. `severity ∈ {1, 2, 3, 4}` представляют собой дискретные индексы заранее откалиброванных наборов параметров деградаций (mild, moderate, strong, severe).
  3. Зафиксировать формат элементарной экспериментальной единицы:
     $$\mathcal{E} = (\text{document\_id}, \text{degradation\_type}, \text{severity}, \text{preprocessing\_config}, \text{ocr\_model}, \text{kie\_model})$$
* **Context:** Для обеспечения строгой сопоставимости результатов между различными типами деградаций необходима единая индексация интенсивности и детерминированная идентификация каждого запуска.
* **Alternatives:** Непрерывная случайная генерация параметров (делает невозможным усреднение и построение кривых деградации) или ручное задание параметров без единой шкалы.
* **Rationale:** Дискретная шкала 0–4 позволяет строить канонические кривые «Severity vs Metric» и двумерные хитмапы, понятные для научной публикации.
* **Consequences:** Для каждого типа деградации в конфигурации должен быть явно описан маппинг индекса severity на физические параметры фильтра.

## ADR-012: Фиксация исследовательского протокола (Research Freeze) и источника SROIE
* **Status:** Accepted (2026-09-26, TASK-003-R2)
* **Decision:**
  1. Объявить исследовательский протокол окончательно зафиксированным (**FROZEN**). Любые последующие изменения требуют явного решения архитектора.
  2. Зафиксировать единственный канонический источник данных (Single Source of Truth):
     * **Repository:** `Kaggle Dataset: urbikn/sroie-datasetv2` (ICDAR 2019 Task 1–3 Cleaned Mirror).
     * **Состав:** 626 train, 347 test (строго парные документы с полным комплектом `.jpg` + `.txt` + `.json`). 14 документов тестового сплита оригинального соревнования, не имевших KIE Ground Truth в Task 3, исключены из KIE-оценки.
  3. Зафиксировать схему сплитов:
     * `train` (626) $\to$ `development` (500) + `validation` (126, seed 42, для калибровки фильтров и severity);
     * `test` (347) $\to$ `main experiment` ($N=100$, seed 42) + `full test verification` ($N=347$). Тестовый сплит строго изолирован от любого тюнинга.
  4. Зафиксировать иерархию препроцессинга B0 / B1 / B2 и отложить утверждение численных параметров фильтров до эмпирической калибровки на `validation` сплите.
  5. Зафиксировать фальсифицируемые гипотезы H1–H4 без жестко зашитых порогов.
* **Context:** Перед переходом к реализации Dataset Adapter необходимо исключить любые неоднозначности в объеме выборки, разбиении данных, формулировках гипотез и протоколе оценки.
* **Alternatives:** Оставлять неразрешенным вопрос 347 vs 361 и смешивать train/validation.
* **Rationale:** Полная прозрачность и однозначность методологии гарантирует строгую воспроизводимость результатов на любом этапе дипломного исследования.
* **Consequences:** Все последующие модули (Dataset Adapter, Degradation Engine, Preprocessor, OCR, KIE) будут реализовываться строго по зафиксированному протоколу.

## ADR-013: OCR Engine Selection and Reading Order Strategy
* **Status:** Accepted (2026-09-26, TASK-006)
* **Decision:**
  1. **Выбор базового OCR-движка:** Зафиксировать RapidOCR (`rapidocr-onnxruntime==1.4.4`) с рантаймом ONNX Runtime (`onnxruntime==1.30.0`) и встроенными весами моделей PP-OCRv4 (`ch_PP-OCRv4_det_infer.onnx`, `ch_PP-OCRv4_rec_infer.onnx`, `ch_ppocr_mobile_v2.0_cls_infer.onnx`).
  2. **Инженерные критерии выбора** (без утверждений о наивысшей точности или ссылок на тестовые бенчмарки):
     * *Полная автономность и офлайн-выполнение:* 100% локальное исполнение без внешних сетевых API или облачных зависимостей.
     * *Портативность:* Легковесный кросс-платформенный рантайм ONNX, не требующий установки системных C++ бинарников (в отличие от Tesseract) или тяжеловесного фреймворка глубокого обучения (PaddlePaddle, PyTorch/CUDA).
     * *Сквозной пайплайн (End-to-End):* Одновременное выполнение детекции текста и распознавания символов за один проход.
     * *Формат выхода:* Предоставление 4-точечных полигонов, осесимметричных bounding box и пословных/построчных оценок уверенности (confidence).
     * *Детерминизм и скорость на CPU:* Стабильное время выполнения на стандартном офисном/ноутбучном оборудовании без дискретной GPU.
  3. **Strict Ground Truth Isolation:**
     * Основной контракт `recognize(image: np.ndarray, document_id: str) -> OCRResult` строго изолирован от любой эталонной разметки (Ground Truth). Ни боксы, ни транскрипции, ни KIE-сущности не могут передаваться в основной метод распознавания.
     * Диагностический режим вынесен в отдельный явный метод `diagnostic_gt_region_recognition(image, document_id, gt_boxes) -> OCRResult`, который изолирован от основного бенчмарка и не вызывается в сценарии `run_ocr_baseline.py`.
  4. **Стратегия порядка чтения (Reading Order):**
     * Реализована детерминированная эвристика двумерной сортировки: кластеризация строк по координате $Y$ с настраиваемым допуском `line_tolerance_factor` (по умолчанию 0.5 от медианной высоты боксов), с последующей сортировкой слева направо по координате $X$ и вторичной стабилизацией по $Y$.
     * Задокументировано, что данная сортировка является инженерной эвристикой для чеков и квитанций и не является универсальным алгоритмом для сложных многоколоночных макетов.
     * Исходные ориентированные 4-точечные полигоны сохраняются в `metadata["raw_quadrilaterals"]`, а координаты `BoundingBox` сохраняются в исходном виде без принудительного клиппинга.
  5. **Метрики качества и нормализация:**
     * Метрики включают CER, WER и строго определенный **Character-NED similarity** ($1.0 - \frac{\text{edit\_distance}}{\max(\text{len}(pred), \text{len}(gt), 1)}$) в диапазоне $[0.0, 1.0]$.
     * Предусмотрен раздельный расчет метрик на сыром тексте (Raw) и нормализованном (Unicode NFC, схлопывание пробелов, удаление управляющих символов), сохраняющий 4 текстовых представления (`raw_pred`, `raw_gt`, `norm_pred`, `norm_gt`).
  6. **Статус реальных данных:**
     * В отсутствие предварительно скачанного архива SROIE в рабочей директории статус бенчмарка фиксируется строго как `REAL-DATA OCR BASELINE: PENDING`. Оценка на фикстурах служит исключительно верификацией целостности кода пайплайна.
* **Context:** Для обеспечения воспроизводимости дипломного пайплайна требовалось выбрать локальный OCR-движок, реализовать метрики оценки и изолировать эталонную разметку от процесса предсказания.
* **Alternatives:**
  * *Tesseract OCR:* Требует внешнего системного бинарника `tesseract.exe`, что создает проблемы с переносимостью между Windows/Linux и снижает воспроизводимость.
  * *EasyOCR / PyTorch:* Требует объемных зависимостей PyTorch (>1 ГБ) и демонстрирует медленный инференс на CPU.
  * *PaddleOCR (полный):* Требует сложной установки PaddlePaddle и специфических бинарных wheel-пакетов под Windows.
* **Rationale:** RapidOCR на базе ONNX Runtime удовлетворяет всем инженерным требованиям к автономности, скорости на CPU и стабильности окружения.
* **Consequences:** В проекте зафиксирован стабильный OCR-компонент, готовый к сквозным экспериментам с деградациями и препроцессингом в последующих задачах.

## ADR-014: Preprocessing Architecture, Primitives and B0/B1/B2 Baseline Protocols
* **Status:** Accepted (2026-09-26, TASK-007)
* **Decision:**
  1. **Архитектурный контракт препроцессинга:** Использовать единый контракт `BasePreprocessor` и DTO `PreprocessingSpec` из `src.core`. Первичный метод `process(image, spec) -> Tuple[np.ndarray, PreprocessingSpec]` строго гарантирует неизменяемость входа (`image.copy()`), валидацию типов (uint8, 2D/3D), детерминизм и pass-through при `spec.enabled == False`. Допускается изменение числа каналов и размерностей (например, Grayscale или Binarization возвращают 2D uint8).
  2. **Состав примитивов предобработки:**
     * *P1 — Grayscale (`GrayscalePreprocessor`):* преобразование RGB/RGBA в 2D uint8 (с использованием стандартных весов яркости).
     * *P2 — Denoise (`DenoisePreprocessor`):* детерминированная фильтрация шума (median, bilateral, fast_nl_means).
     * *P3 — CLAHE (`CLAHEPreprocessor`):* локальное контрастное выравнивание гистограммы (прямое для 2D, через L-канал пространства CIE LAB для RGB без искажения цветопередачи).
     * *P4 — Adaptive Binarization (`BinarizationPreprocessor`):* адаптивная бинаризация (Gaussian, Mean, Otsu) с гарантированным выходом $\{0, 255\}$ uint8 (0 = текст, 255 = фон).
     * *P5 — Deskew (`DeskewPreprocessor`):* компенсация геометрического перекоса страницы.
  3. **Эвристика устранения перекоса (Deskew Strategy):**
     * Оценка доминирующего угла наклона текста производится исключительно по визуальным признакам самого изображения (детекция границ Canny + Probabilistic Hough Line Transform с вычислением медианы углов ориентированных линий).
     * Строгая изоляция Ground Truth: метод не принимает и не использует эталонные bounding boxes или транскрипции.
     * Ограничение максимального угла коррекции $[-\theta_{max}, \theta_{max}]$ (по умолчанию $\pm 15^\circ$) и заполнение добавленных полей белым цветом (`borderValue=255`).
     * Зафиксировано, что данный метод является инженерной эвристикой для текстовых документов и чеков, а не универсальным решением для произвольных сложных макетов.
  4. **Аналитические базисы B0 / B1 / B2:**
     * $B_0$: исходное изображение $\to$ OCR $\to$ метрики;
     * $B_1$: деградированное изображение $\to$ OCR $\to$ метрики;
     * $B_2$: деградированное изображение $\to$ препроцессинг $\to$ OCR $\to$ метрики;
     * Модули препроцессинга не содержат логики вычисления метрик (CER/WER/NED); оценка полностью отделена в слой `src/evaluation/`.
  5. **Статус параметров:**
     * Начальные параметры препроцессинга зафиксированы как `provisional` (предварительные); финальная калибровка параметров препроцессинга на валидационном сплите SROIE ($N=126$) ожидает появления полного датасета (`REAL-DATA PREPROCESSING BASELINE: PENDING`).
* **Context:** Для исследования устойчивости OCR к деградациям и эффективности методов их компенсации (RQ2/H2, RQ3/H3) необходим изолированный и воспроизводимый слой предобработки с поддержкой сравнительных базисов B0/B1/B2.
* **Alternatives:** Использование нейросетевых диффузионных/GAN методов восстановления (недетерминированы, тяжеловесны, вносят артефакты галлюцинаций текста) или жесткое вшивание параметров в код без YAML-конфигурации.
* **Rationale:** Модульная архитектура классических CV-примитивов на базе OpenCV обеспечивает высокую скорость на CPU, строгую воспроизводимость и интерпретируемость.
* **Consequences:** В проекте реализован полный сквозной пайплайн $B_0/B_1/B_2$, готовый к проведению полномасштабных экспериментов после размещения данных.

## ADR-015: OCR Stack Refresh (PP-OCRv6) and Reproducibility Lock
* **Status:** Accepted (2026-09-26, TASK-008)
* **Decision:**
  1. **Актуализация OCR model stack:** Перевести базовый OCR-слой с устаревшей связки PP-OCRv4 (`rapidocr-onnxruntime==1.4.4`) на современный пакет RapidOCR (`rapidocr==3.9.2`) с рантаймом ONNX Runtime (`onnxruntime==1.30.0`) и моделями поколения PP-OCRv6 (small tier):
     * Detector: `PP-OCRv6_det_small.onnx` (9,929,594 байт, SHA256: `090f04abcd9d9a7498bc4ebf677e4cb9bdce1fe4197ddb7e529f1ef44e1ff94f`);
     * Recognizer: `PP-OCRv6_rec_small.onnx` (21,234,383 байт, SHA256: `6f327246b50388f3c176ae304bd95767ea6dc0c9ae92153ef8cbe210b3c14884`);
     * Classifier: `ch_ppocr_mobile_v2.0_cls_mobile.onnx` (585,532 байт, SHA256: `e47acedf663230f8863ff1ab0e64dd2d82b838fceb5957146dab185a89d6215c`).
  2. **Криптографическая фиксация моделей (Reproducibility Lock):**
     * Вместо доверия конфигурационным строкам реализована динамическая интроспекция активной сессии ONNX Runtime (`OrtInferSession.session._model_path`), вычисление фактического SHA256 хеша каждого файла на диске и сравнение с эталонными значениями.
     * Model path resolution currently relies on a private RapidOCR wrapper attribute and is therefore version-sensitive. Если данный приватный атрибут пропадает или файл отсутствует, генерация манифеста аварийно завершается громкой ошибкой (fail loudly) без замалчивания.
     * При несовпадении хеша или отсутствии файла выполнение блокируется (`verify_model_stack()` возвращает ошибки).
  3. **Сохранение контракта BaseOCREngine и Strict GT Isolation:**
     * Контракт `recognize(image: np.ndarray, document_id: str) -> OCRResult` сохранен без изменений.
     * Никакие эталонные данные (GT boxes, transcripts, entities) не передаются в метод распознавания.
     * Внутрь OCR-движка не внедряются скрытые методы улучшения качества (денойз, CLAHE, дескев); они изолированы в модуле `src/preprocessing/`.
  4. **Экспорт машиночитаемого манифеста:**
     * При запуске базового скрипта `scripts/run_ocr_baseline.py` формируется файл `experiments/runs/ocr_stack_manifest.json`, содержащий четко разделенные секции:
       * `configured`: заявленные в конфигурации параметры и модели;
       * `resolved`: фактические пути, размеры, SHA256 хеши и статус валидации файлов;
       * `environment`: версии пакетов (`rapidocr`, `onnxruntime`, `opencv`, `numpy`), ОС и провайдер исполнения (`CPUExecutionProvider`);
       * `resize_policy`: блок с подразделами `configured`, `resolved` и флагом `verified: true`.
  5. **Аудит и фиксация политики ресайза (Resize Policy Lock):**
     * Эксплицитно задокументированы параметры ресайза RapidOCR:
       * глобальный ресайз: `max_side_len = 2000`, `min_side_len = 30` с округлением до кратных 32;
       * детекционный ресайз: `det_limit_side_len = 736`, `det_limit_type = 'min'`;
       * интерполяция: билинейная (`cv2.INTER_LINEAR`).
     * **Интерпретация для B0/B1/B2:** B0, B1 and B2 use the same OCR-side resize policy and the same OCR configuration. The resulting resized dimensions may legitimately differ because the input images differ after degradation/preprocessing. Не утверждается, что физический результат ресайза обязан быть одинаковым.
  6. **Статус реальных данных:**
     * Статус реального SROIE бенчмарка сохранен как `REAL-DATA OCR BASELINE: PENDING`. Все метрики в отсутствие полного скачанного датасета помечены как синтетические проверочные.
* **Context:** Для обеспечения научной достоверности дипломного исследования необходимо исключить любые скрытые факторы (изменение весов моделей, автоматические скрытые загрузки, различие параметров ресайза) при переходе к актуальной архитектуре PP-OCRv6.
* **Alternatives:**
  * Остаться на PP-OCRv4 (устаревшая версия 2023 года с меньшей точностью распознавания плотного текста квитанций).
  * Использовать серверный PaddleOCR через REST API (нарушает автономность и воспроизводимость).
* **Rationale:** PP-OCRv6 was selected as the primary OCR model family because it is the current verified model generation available through the selected RapidOCR/ONNX Runtime CPU stack while preserving the project's offline and reproducibility requirements. Заявления о превосходстве точности над PP-OCRv4 не делаются без проведения контролируемого эксперимента на полном датасете SROIE. Измеренная в смоук-тесте задержка на CPU является аппаратно-зависимой и не используется как научное утверждение о производительности.
* **Consequences:** В проекте зафиксирован современный, криптографически верифицированный OCR-слой с идентичной конфигурацией ресайза для всех последующих стадий экспериментальной матрицы.

## ADR-016: Downstream KIE Baseline Strategy and Evaluation Protocols
* **Status:** Accepted (2026-09-26, TASK-009 / TASK-009-R1)
* **Decision:**
  1. **Строгий OCRResult-only контракт инференса:**
     * Контракт KIE-движка в `src/core/contracts.py` зафиксирован как:
       `extract(ocr_result: OCRResult, document_id: str) -> KIEResult`.
     * Аргумент `image: Optional[np.ndarray]` полностью удален из production KIE API. Если будущие мультимодальные модели (например, LayoutLM) потребуют визуальных эмбеддингов или кропов изображений, это будет выделено в отдельный архитектурный контракт через последующий ADR.
     * Строгая изоляция Ground Truth (Zero GT Leakage): на вход инференса KIE передается исключительно DTO `OCRResult` и идентификатор документа. Никакие эталонные данные (GT bounding boxes, GT transcripts, GT entity annotations, dataset adapter) не передаются и не доступны KIE-модели.
  2. **Модульная архитектура правил (Rule-Based KIE Baseline):**
     * Модуль `src/kie/` реализует детерминированное извлечение 4 целевых полей SROIE (`company`, `date`, `address`, `total`) через примитивы в `src/kie/rules/`.
     * Каждое правило формирует кандидатов `FieldCandidate` с нормализованной уверенностью `[0.0, 1.0]`, списком индексов токенов-источников (`token_indices`) и именем примененного правила.
     * Реализовано сохранение аудиторского следа происхождения токенов (`metadata["field_provenance"]`) для каждого извлеченного поля.
     * **Ограничения переноса и анти-оверфиттинг:** Эвристики (ключевые слова юридических форм SDN BHD, малайзийские названия штатов, шаблоны дат и структуры заголовков) калиброваны под структуру квитанций SROIE и носят статус предварительных (provisional). Они не объявляются универсально применимыми для произвольных документов. Правила не содержат захардкоженных идентификаторов документов или специфических координат конкретных чеков.
  3. **Политика обработки агрессивного фоллбэка (Total Fallback Policy):**
     * Эвристика «наибольшее числовое значение на чеке является total» является агрессивной и по умолчанию строго отключена (`fallback_largest_amount: false`).
     * При явном включении в конфигурации для целей абляционного анализа кандидату, найденному по фоллбэку, назначается штраф к уверенности (`fallback_penalty: 0.5`).
  4. **Двухуровневый протокол оценки (Dual Evaluation Framework):**
     * В `src/evaluation/kie_metrics.py` реализовано строгое структурное разделение метрик:
       * `analytical_metrics`: пополевые Precision, Recall, F1 (как для сырых строк `raw`, так и для нормализованных `normalized`), Macro Precision / Recall / F1 по всем 4 полям, а также независимые показатели `raw_doc_em` и `normalized_doc_em` (доля документов, в которых абсолютно все поля совпали с эталоном);
       * `sroie_official_compatible`: микро-метрики Precision, Recall и Hmean (F1) на уровне сущностей согласно официальному протоколу соревнований ICDAR SROIE Task 3.
  5. **Политика нормализации значений (Normalization Policy):**
     * Текстовые поля нормализуются через Unicode NFC, приведение к нижнему регистру, схлопывание пробельных символов и удаление граничной пунктуации с обязательным сохранением внутренней пунктуации (слэши в датах `25/12/2018`, дефисы).
     * Суммы (`total`) нормализуются с очисткой от валютных префиксов (`$`, `RM`, `MYR`) и пробелов с гарантированным сохранением десятичной структуры чисел (например, `$10.00` $\to$ `10.00`, `10` $\to$ `10.00`).
  6. **Аудиторский след порядка исполнения (Execution Order Audit):**
     * Скрипт пайплайна `scripts/run_kie_baseline.py` принудительно исполняет и протоколирует фазы в строгом порядке:
       `ocr_inference` $\to$ `kie_inference` $\to$ `gt_loading` $\to$ `evaluation`.
     * В отчете `experiments/runs/kie_baseline_report.json` фиксируется массив `execution_order_audit.enforced_phases` и индивидуальный хронометраж каждого шага.
  7. **Статус данных бенчмарка:**
     * Статус выполнения зафиксирован как `PENDING_REAL_DATA`. Все метрики, полученные на локальных синтетических фикстурах, помечены как предварительные верификационные. Окончательные значения на полном датасете SROIE будут вычислены после его загрузки.
* **Context:** Для дипломного исследования влияния деградаций на downstream-задачи (RQ4/H4) необходим детерминированный, прозрачный и свободный от утечек эталона baseline для KIE поверх ранее зафиксированного OCR-стека.
* **Alternatives:**
  * Использование end-to-end мультимодальной нейросетевой модели (LayoutLM, Donut), что усложняет интерпретируемость влияния деградаций OCR на KIE и требует GPU-ресурсов для обучения.
  * Прямая передача GT-регионов или изображения в KIE-модель (нарушает чистоту каскадного эксперимента B0/B1/B2 и приводит к GT-leakage).
* **Rationale:** Правилосодержащий baseline на чистом `OCRResult` обеспечивает 100% интерпретируемость, строгую изоляцию эффектов OCR и однозначную трассировку ошибок downstream-этапа к качеству текста OCR.
* **Consequences:** Реализован и верифицирован базовый KIE-слой с фабрикой, правилами, двойной системой метрик и сквозным раннером. Кодовая база подготовлена к запуску полной экспериментальной матрицы.
