# Architectural Decision Records (ADR)

Журнал фиксации архитектурных решений проекта «Качество скана и устойчивость OCR/KIE к деградациям».

---

## ADR-001: Модульная структура репозитория
* **Status:** Accepted (2026-09-26)
* **Decision:** Организовать проект в виде независимых пакетов внутри `src/`: `degradation`, `preprocessing`, `ocr`, `kie`, `evaluation`, `visualization`, с четким разделением конфигураций (`configs/`), скриптов (`scripts/`), тестов (`tests/`) и Kaggle-окружения (`kaggle/`).
* **Context:** Исследовательский проект требует гибкости для изолированного тестирования каждого этапа пайплайна без взаимного спагетти-кода.
* **Alternatives:** Монолитный скрипт или организация вокруг Jupyter-ноутбуков.
* **Rationale:** Ноутбуки плохо поддаются версионированию, автоматизированному тестированию и запуску матриц экспериментов. Четкая структура пакетов обеспечивает модульность и поддерживаемость.
* **Consequences:** Необходимость определять строгие контракты данных (DTO) между слоями.

## ADR-002: Конфигурационное управление экспериментами (Config-Driven Architecture)
* **Status:** Accepted (2026-09-26)
* **Decision:** Все параметры экспериментов (тип деградации, severity, шаги препроцессинга, настройки OCR, правила метрик, random seed) задаются через иерархические YAML-файлы в директории `configs/`.
* **Context:** Проведение матричных экспериментов и обеспечение их научной воспроизводимости требует исключить хардкод параметров в исполняемом коде.
* **Alternatives:** Передача всех параметров через аргументы командной строки (argparse/click) или глобальные переменные в Python файлах.
* **Rationale:** Файлы YAML легко версионируются, валидируются и могут сохраняться в директорию запуска вместе с полученными метриками для 100% аудируемости результатов.
* **Consequences:** Требуется наличие библиотеки PyYAML и схемы валидации конфигурационных файлов.

## ADR-003: Разделение слоев Degradation, Preprocessing, OCR, KIE и Evaluation
* **Status:** Accepted (2026-09-26)
* **Decision:** Каждый из пяти этапов экспериментального пайплайна проектируется как полностью независимый компонент с контрактом обмена через простые типы (`numpy.ndarray`, DTO/dataclasses):
  - Degradation: `(Image, severity, seed) -> DegradedImage`
  - Preprocessing: `(DegradedImage, params) -> EnhancedImage`
  - OCR: `(Image) -> OCRResult (text, bboxes, confidences)`
  - KIE: `(OCRResult, Image?) -> KIEResult (fields, confidences)`
  - Evaluation: `(Prediction, GroundTruth) -> Metrics`
* **Context:** Необходимо иметь возможность заменять один компонент (например, менять метод OCR или отключать препроцессинг) без модификации кода остальных модулей.
* **Alternatives:** Сквозной пайплайн, где препроцессинг встроен в модуль OCR, а KIE жестко завязан на конкретный формат вывода конкретной OCR-библиотеки.
* **Rationale:** Сквозная привязка делает невозможным проведение абляционных исследований (ablation study) и изоляцию источника ошибок.
* **Consequences:** Потребуется написать адаптеры для приведения вывода различных OCR/KIE библиотек к единому формату DTO.

## ADR-004: Протокол воспроизводимости (Reproducibility Protocol)
* **Status:** Accepted (2026-09-26)
* **Decision:** Каждый генератор деградаций и случайных преобразований должен явно принимать и фиксировать `seed`. Для каждого эксперимента фиксируется глобальный random seed, записываемый в итоговый артефакт.
* **Context:** В научных исследованиях недетерминированные искажения изображений делают невозможным прямое попарное сравнение эффективности алгоритмов предобработки.
* **Alternatives:** Случайная генерация на лету без фиксации состояния генератора псевдослучайных чисел.
* **Rationale:** Одинаковый исходный документ + одинаковый seed + одинаковый severity обязаны давать попиксельно идентичную деградацию.
* **Consequences:** Необходимость написания unit-тестов, проверяющих детерминизм деградаций по seed.

## ADR-005: Выделение Kaggle как отдельной execution target
* **Status:** Accepted (2026-09-26)
* **Decision:** Выделить директорию `kaggle/` для размещения скриптов автоматизации сборки и запуска ядра через официальный Kaggle API (`kaggle kernels push`).
* **Context:** Выполнение полного матричного эксперимента требует GPU-ресурсов, которые могут быть предоставлены облачной платформой Kaggle.
* **Alternatives:** Разработка непосредственно в веб-ноутбуках Kaggle с последующим ручным переносом кода в локальный репозиторий.
* **Rationale:** Локальная разработка в IDE с версионированием в Git и отправка готовых скриптов в Kaggle через CLI предотвращает рассинхронизацию кодовой базы и потерю истории коммитов.
* **Consequences:** Требуется разработать скрипт упаковки локального пакета `src/` для автономного импорта внутри окружения Kaggle.

## ADR-006: Дискретная шкала severity деградаций (целые числа 0–4)
* **Status:** Accepted (2026-09-26)
* **Decision:** Зафиксировать уровни интенсивности деградаций в `DegradationSpec` в виде строго целочисленной шкалы от 0 до 4:
  - `0`: исходное изображение без изменений (Identity / Clean baseline);
  - `1`: слабая деградация (mild);
  - `2`: умеренная деградация (moderate);
  - `3`: сильная деградация (strong);
  - `4`: критическая/разрушительная деградация (severe).
* **Context:** Для построения робастных кривых (Robustness curves: качество распознавания vs степень искажения) требуется дискретная ось X с сопоставимыми градациями между различными типами физических искажений (размытие, шум, сжатие, тени).
* **Alternatives:** Непрерывный float диапазон [0.0, 1.0] или задание физических параметров напрямую в эксперименте.
* **Rationale:** Дискретные уровни 0–4 позволяют легко агрегировать результаты по всей тестовой выборке и сравнивать разные алгоритмы в одинаковых реперных точках. Физические параметры (например, $\sigma$ размытия или Quality JPEG) однозначно маппируются на уровень severity внутри конфигурации генератора.
* **Consequences:** Каждый генератор деградаций обязан реализовать однозначное отображение дискретного уровня 0–4 на свои физические параметры.

## ADR-007: Использование стандартных dataclasses для DTO без внешних валидаторов
* **Status:** Accepted (2026-09-26)
* **Decision:** Реализовать все DTO в `src/core/schemas.py` на базе стандартных `dataclasses` со строгой валидацией в методе `__post_init__` и явными методами `to_dict()` и `from_dict()`.
* **Context:** Требовалось обеспечить строгую типизацию, проверку инвариантов и сериализацию без раздувания зависимостей проекта.
* **Alternatives:** Использование библиотеки Pydantic (v1/v2) или Attrs.
* **Rationale:** Введение Pydantic на этапе core-контрактов создает лишнюю тяжелую зависимость с потенциальными проблемами совместимости между версиями Python и платформами (особенно при переносе в Kaggle / минимальные контейнеры). Стандартный модуль `dataclasses` обеспечивает нулевой оверхед, отсутствие внешних зависимостей и прозрачное управление логикой валидации.
* **Consequences:** Необходимость явного написания логики валидации и десериализации вложенных структур в методах `from_dict()`.

## ADR-008: Выбор базового датасета SROIE и архитектура Dataset Adapter
* **Status:** Accepted (2026-09-26, уточнён в TASK-003-R1)
* **Decision:** 
  1. Выбрать **SROIE (ICDAR 2019 Robust Reading Challenge on Scanned Receipts)** в качестве Primary Benchmark для исследования устойчивости OCR/KIE к деградациям. В качестве Secondary Cross-Domain Validation зафиксировать **FUNSD** (без обязательной реализации в MVP), а **DocILE** — как Future Enterprise Extension.
  2. Зафиксировать архитектуру загрузки через абстрактный интерфейс `BaseDatasetAdapter` с конкретной реализацией `SROIEAdapter`.
  3. Для дипломных экспериментов зафиксировать подвыборки: Smoke test ($N=3..5$), Development ($N=25$), Main research experiment ($N=100$ из тестового сплита) с возможностью финального прогона на полном сплите ($N=361$).
  4. Зафиксировать, что `severity=0` означает оригинальное изображение из датасета (с его естественными артефактами бумаги и печати), а не идеальный синтетический документ.
  5. Запретить подбор гиперпараметров деградаций и препроцессинга на основном тестовом сплите (защита от Data Leakage).
* **Context:** Для исследования влияния физических деградаций сканов на связку OCR $\to$ KIE необходим датасет реальных документов с подтвержденным и независимым Ground Truth одновременно для распознавания текста (построчная транскрипция с координатами) и семантических полей (`company`, `date`, `address`, `total`), доступный для пакетного исполнения на Kaggle.
* **Alternatives:** 
  * FUNSD (слишком малый сплит $N=50$, исходно зашумлен архивными артефактами, KIE в виде графа вопрос-ответ).
  * CORD (индонезийский язык, 30 категорий меню усложняют интерпретацию).
  * DocILE (закрытый доступ по токену, многостраничные PDF, десятки гигабайт, перегрузят ресурсы).
* **Rationale:** SROIE является признанным академическим бенчмарком с RGB сканами/фотографиями, четкой 4-полевой KIE схемой, английским языком и встроенной доступностью на платформе Kaggle (`urbikn/sroie-datasetv2`). Архитектура `BaseDatasetAdapter` позволяет в будущем безболезненно подключить любой другой датасет.
* **Consequences:** Специфика документов ограничена кассовыми чеками и квитанциями. Для работы с SROIE требуется адаптер, преобразующий Task 1/2 `.txt` файлы и Task 3 `.json` в наши контракты `DocumentMetadata`, `OCRGroundTruth` и `KIEGroundTruth`.

## ADR-009: Двухуровневый протокол оценки OCR (End-to-End как Primary, GT-Region как Diagnostic)
* **Status:** Accepted (2026-09-26)
* **Decision:** Зафиксировать два взаимодополняющих протокола оценки OCR:
  1. **Primary Protocol (End-to-End OCR):** изображение подается целиком на вход OCR-модели, оценивается качество связки детекция + распознавание + reading order $\to$ KIE.
  2. **Diagnostic Protocol (GT-Region Recognition):** текст распознается по кропам эталонных bounding boxes из Ground Truth, что позволяет строго изолировать ошибки распознавания символов от ошибок детекции границ текста при анализе аномалий.
* **Context:** Деградации изображения одновременно влияют и на локализацию текстовых блоков (Detection), и на транскрипцию символов (Recognition). Необходимо исследовать реальный промышленный сквозной эффект, но иметь механизм точной диагностики первопричин сбоев.
* **Alternatives:** Использовать только Recognition по GT боксам (оторвано от реальности) либо только End-to-End (не позволяет понять, почему упало качество — из-за детектора или распознавателя).
* **Rationale:** End-to-End является основным сценарием Document AI, а GT-Region протокол используется для глубокого исследовательского анализа в дипломной работе.
* **Consequences:** Движок OCR должен поддерживать как режим полного распознавания изображения, так и распознавание по заданным полигонам/боксам.

## ADR-010: Политика неизменяемого Raw Ground Truth и изолированной семантической нормализации KIE
* **Status:** Accepted (2026-09-26)
* **Decision:**
  1. Датасет-адаптер обязан отдавать Ground Truth в строго неизменном, сыром виде (**Immutable Raw GT**). Запрещено модифицировать эталонный текст или форматы дат/сумм на уровне загрузки данных.
  2. Оценка OCR (CER, WER) производится по прямому строковому сопоставлению с Raw OCR GT.
  3. Для оценки KIE вводится централизованный модуль симметричной нормализации `Normalize()`, применяемый одинаково к предсказанию модели и эталону в момент вычисления метрик:
     $$\text{Matched} \iff \text{Normalize}(V_{pred}) == \text{Normalize}(V_{gt})$$
* **Context:** Без нормализации метрика KIE Exact Match катастрофически занижается из-за банальных различий форматирования (`01/02/2020` vs `2020-02-01`), однако мутация исходного GT на уровне адаптера лишает исследование объективности и маскирует реальный текст.
* **Alternatives:** Сравнение строк "как есть" (занижает F1) либо изменение файлов разметки самого датасета (нарушает воспроизводимость и чистоту бенчмарка).
* **Rationale:** Изолированная симметричная нормализация в момент evaluation гарантирует чистоту данных и объективность замеров.
* **Consequences:** Необходимость строгой спецификации и тестирования правил нормализации для каждого типа целевых полей.

## ADR-011: Семантика шкалы Severity и спецификация экспериментальной единицы
* **Status:** Accepted (2026-09-26)
* **Decision:**
  1. `severity = 0` строго определяется как контрольный оригинал документа из датасета (Control Reference) без синтетических деградаций.
  2. `severity ∈ {1, 2, 3, 4}` представляют собой дискретные индексы заранее откалиброванных наборов параметров деградаций (mild, moderate, strong, severe).
  3. Зафиксировать формат элементарной экспериментальной единицы:
     $$\mathcal{E} = (\text{document\_id}, \text{degradation\_type}, \text{severity}, \text{preprocessing\_config}, \text{ocr\_model}, \text{kie\_model})$$
* **Context:** Для обеспечения строгой сопоставимости результатов между различными типами деградаций необходима единая индексация интенсивности и детерминированная идентификация каждого запуска.
* **Alternatives:** Непрерывная случайная генерация параметров (делает невозможным усреднение и построение кривых деградации) или ручное задание параметров без единой шкалы.
* **Rationale:** Дискретная шкала 0–4 позволяет строить канонические кривые «Severity vs Metric» и двумерные хитмапы, понятные для научной публикации.
* **Consequences:** Для каждого типа деградации в конфигурации должен быть явно описан маппинг индекса severity на физические параметры фильтра.

## ADR-012: Фиксация исследовательского протокола (Research Freeze) и источника SROIE
* **Status:** Accepted (2026-09-26, TASK-003-R2)
* **Decision:**
  1. Объявить исследовательский протокол окончательно зафиксированным (**FROZEN**). Любые последующие изменения требуют явного решения архитектора.
  2. Зафиксировать единственный канонический источник данных (Single Source of Truth):
     * **Repository:** `Kaggle Dataset: urbikn/sroie-datasetv2` (ICDAR 2019 Task 1–3 Cleaned Mirror).
     * **Состав:** 626 train, 347 test (строго парные документы с полным комплектом `.jpg` + `.txt` + `.json`). 14 документов тестового сплита оригинального соревнования, не имевших KIE Ground Truth в Task 3, исключены из KIE-оценки.
  3. Зафиксировать схему сплитов:
     * `train` (626) $\to$ `development` (500) + `validation` (126, seed 42, для калибровки фильтров и severity);
     * `test` (347) $\to$ `main experiment` ($N=100$, seed 42) + `full test verification` ($N=347$). Тестовый сплит строго изолирован от любого тюнинга.
  4. Зафиксировать иерархию препроцессинга B0 / B1 / B2 и отложить утверждение численных параметров фильтров до эмпирической калибровки на `validation` сплите.
  5. Зафиксировать фальсифицируемые гипотезы H1–H4 без жестко зашитых порогов.
* **Context:** Перед переходом к реализации Dataset Adapter необходимо исключить любые неоднозначности в объеме выборки, разбиении данных, формулировках гипотез и протоколе оценки.
* **Alternatives:** Оставлять неразрешенным вопрос 347 vs 361 и смешивать train/validation.
* **Rationale:** Полная прозрачность и однозначность методологии гарантирует строгую воспроизводимость результатов на любом этапе дипломного исследования.
* **Consequences:** Все последующие модули (Dataset Adapter, Degradation Engine, Preprocessor, OCR, KIE) будут реализовываться строго по зафиксированному протоколу.
